## 2. How it works

- **Stable identity.** `txn_group_id` (e.g. `SYN_TXN-000014`) is the immutable business key. Meaning lives in revisions (`revision_no` 1, 2, … with `prev_revision_id` links). The account/investor master comes from the frozen M2 output, upserted idempotently; M2 `posting_sequence` and simulated `recorded_at` are preserved.
- **Two clocks.** `effective_date` is valid time; `recorded_at` + `system_period` is knowledge time. `get_as_of(K)` returns the greatest `recorded_at ≤ K` revision per transaction, excluding `VOIDED`. A correction recorded after K1 therefore cannot move K1, always moves K2 — proven by test.
- **Corrections.** `REPLACE` changes an amount/units/date; `VOID` appends a `VOIDED` revision; `REVERSE_AND_REPLACE` changes the scheme. Each correction is one `correction_group` and one new revision, applied in a single DB transaction along with the prior-period close in the projection and the current-version upsert. `core.txn_revision` itself is never updated or deleted (trigger enforced). Linked legs (SIP two-leg, SWITCH two-leg) recompute atomically; the five-day allotment rule applies to the candidate.
- **Validity.** Before committing, the service replays all posting legs for the account in `(posting_date, posting_sequence, txn_group_id)` order with `Decimal` arithmetic. A first negative cash or units figure aborts the whole group with `INSUFFICIENT_CASH_DOWNSTREAM` / `NEGATIVE_UNITS_DOWNSTREAM`; other rejections include `INVALID_REFERENCE`, `NON_MONOTONIC_RECORDED_AT`, `INVALID_CORRECTION_TYPE`, `MISSING_NAV_ALLOTMENT`. Rejections are persisted as `correction_rejection` rows; a rejected correction leaves no group, no revision and no projection change (asserted by test).
- **No-overlap.** `EXCLUDE USING gist (txn_group_id WITH =, system_period WITH &&)` makes overlap impossible at the storage layer; a raw overlapping insert raises `ExclusionViolation` in test.
- **Projection.** `txn_version_current` always mirrors the latest revision; deleting it and rebuilding from revisions yields the identical table (asserted by test).

## 4. Three interviewer questions

**Q1. Why not just update the transaction row on correction?**
Because a report generated at K1 must still reproduce. Overwriting destroys the value K1 saw. The ledger appends a new revision and closes the prior knowledge interval, so both the K1 and K2 answers remain queryable.

**Q2. What stops two versions of one transaction being current at once?**
Two layers: the application closes the prior period before inserting the new one, and PostgreSQL enforces `EXCLUDE (txn_group_id WITH =, system_period WITH &&)`. Even a buggy service cannot create an overlap — the database rejects it.

**Q3. How do you know a correction does not bankrupt the account later?**
You replay the whole account with the candidate in place, in posting-sequence order. The first negative cash or units step vetoes the entire group. This is a posting-validity simulation (M3), not a valuation — no position is ever valued.

## 5. Limitations for review

- One correction group per operation (one new revision). Bulk multi-transaction groups are schema-legal but not implemented (D-043).
- M2 emitted one `allotment_date` for switches; ingestion mirrors it to both legs. Split-date switch corrections compute the two dates independently.
- Equal `recorded_at` on the same transaction is rejected as `NON_MONOTONIC_RECORDED_AT`.
- Batch provenance (dataset hash) is in the ingestion report, not a ledger table; M7 may add one.
- Downstream replay is O(all transactions for the account) per correction — a documented cost for dataset sizes in scope.
