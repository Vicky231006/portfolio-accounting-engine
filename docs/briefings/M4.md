## 1. What was built

M4 adds as-of positions and NAV valuation on top of the frozen M1–M3 contracts (PRD §5.3, §8; FR-B5, FR-B6; DECISIONS D-049–D-051):

- `src/bitemporal_ledger/valuation/models.py` — immutable result types (`PositionsResult`, `ValuationResult`, `NavPrice`, `ValuedHolding`, `Holding`) and explicit errors (`ValuationError`, `InvariantError`).
- `src/bitemporal_ledger/valuation/service.py` — `ValuationService`: `positions(account_id, valid_date, known_as_of)` replaying visible M3 revisions in `(posting_date, posting_sequence, txn_group_id)` order; `value(...)` pricing holdings from the M1 snapshot with the five-day stale-carry policy, fresh/stale split and reconciliation invariant.
- `tests/integration/test_positions.py` — 8 database tests covering every required scenario.

No migration was needed (both services are reads over M1–M3 tables). No TWR, Modified Dietz, XIRR or sensitivity code was added.

## 2. How it works

- **Positions.** `get_as_of(K)` gives the revisions the system knew at K (the current projection is never read). Each revision expands to posting legs on its own allotment dates; only legs `posting_date <= valid_date` apply, on the M3 replay order. Zero opening balances; funding is an explicit `CONTRIBUTION`.
- **Valuation.** Each holding's price is the latest observation at/before `valid_date` in the parameterised snapshot. Fresh (same day) prices go to `fresh_value`; 1–5-day-old prices are carried forward, flagged, and go to `stale_value`; 6+ days or none raises `STALE_BEYOND_LIMIT` / `MISSING_NAV` and aborts the whole valuation. `holdings_value = Σ(units × price)` (2 dp), `portfolio_value = cash + holdings_value`, with the fresh+stale reconciliation asserted in `Decimal`.
- **Scheme identity** is the AMFI code; there is no name matching and no re-interpretation of FundLens mapping.

## 4. Three interviewer questions

**Q1. Why not read positions from the current table?**
Because the current table only knows K-now. A report at K1 must still see what K1 knew. Deriving from `get_as_of(K)` is what makes the same `valid_date` show different holdings at K1 and K2 after a backdated correction.

**Q2. When is a NAV "stale" and when is it an error?**
Same day is fresh; 1–5 days old is carried forward and labelled stale (and summed separately); 6+ days or no NAV at all is an explicit failure, aborting the whole valuation. No caller can mistake a stale price for a real one.

**Q3. How do you know the valuation ties to the ledger?**
The same leg replay that produces cash and units is then priced: every holding line is `units × price` and the total is `cash + Σ holding`. The fresh/stale split is asserted to recombine exactly, and any negative cash/units encountered mid-replay raises an invariant error — the method never clamps.

## 5. Limitations for review

- One stale limit (default 5 days), parameterised per call.
- Valuation is a point-in-time snapshot; no returns are computed (M5).
- Positions are computed on demand; no holdings table is stored.
- Scheme names are not carried (identity is the AMFI code only).
