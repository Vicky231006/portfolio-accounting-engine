## 2. Why this component exists

A portfolio accounting project can look complete while being financially indefensible. Two common failure modes are:

1. **Conflating valid time and knowledge time.** A backdated correction overwrites history, so the old report cannot be reproduced.
2. **Conflating return measures.** TWR, Modified Dietz and XIRR answer different questions, but a dashboard shows one “return” number without its convention.

M0 forces both issues into the open before code:

- The K1/K2 fixture proves what must remain unchanged and what must change.
- The TWR/Modified Dietz/XIRR fixtures prove that the three measures are different and why.
- The NAV contract proves that real market data can be traced to a source file and checksum.
- The rounding and switch fixtures prove that residual cash is handled explicitly, not lost.

## 3. How it works, in plain English

### 3.1 The two time axes

- **Valid time (effective date):** when the transaction economically applies. A purchase effective 10 January affects the 10 January position.
- **Knowledge time (recorded time):** when the system accepted that version. A correction recorded 5 February is invisible to a report generated at 31 January 09:00, even though it changes the 10 January effective position.

A query therefore takes both a valid date and a knowledge timestamp. The K1 report uses only versions known by K1. The K2 query uses later versions. The old report is not “wrong”; it is a true record of what was known then.

### 3.2 The three return measures

- **TWR** measures the portfolio's investment performance, removing the timing of external contributions and withdrawals. It needs valuations around flows.
- **Modified Dietz** approximates the period return using weighted external flows when daily valuations around every flow are unavailable.
- **XIRR** measures the investor's money-weighted annualised return from dated cash flows, including the terminal value.

They are not interchangeable. The fixture in `docs/METHODOLOGY.md` shows TWR `15.2381%` versus XIRR `6.5248%` for the same two-contribution example.

### 3.3 The NAV contract

FundLens already stores AMFI NAV observations. This project does not re-implement AMFI ingestion or scheme mapping. Vicky selected Option A: consume the canonical CSV from the verified raw-file fallback, using FundLens's parser as a read-only reference. Do not query the FundLens database or access its running volumes.

- scheme identity = stable AMFI scheme code;
- NAV = `NUMERIC(20,6)`;
- date = `DATE`;
- provenance = source file SHA-256, URL, retrieval time and scope hash.

The contract was verified from FundLens migrations, parser code, the actual raw files and FundLens's audited results. The live `core.fact_nav` query will not be executed. The 86-vs-85 raw-file reconciliation has been documented with filenames, checksums, date ranges and row-level differences.

### 3.4 The rounding rule

A purchase instructed by amount can produce a fractional unit count. If units are rounded up, the cash debit can exceed the instruction. The recommended rule is:

- units: 3 dp, ROUND_DOWN for amount-instructed purchases;
- amounts: 2 dp, ROUND_HALF_UP;
- NAV: as published, never rounded;
- residual cash: retained and reported, never discarded.

The switch fixture shows why: `100` units at NAV `20.0000` gives `2,000.00`; at target NAV `30.0000`, half-up would buy `66.667` units costing `2,000.01` (negative residual). ROUND_DOWN buys `66.666` units costing `1,999.98`, leaving `0.02` cash.

## 4. Important formulas and tables

### 4.1 TWR

```
r_t = (V_t - V_(t-1) - CF_t) / (V_(t-1) + CF_t)
TWR = product(1 + r_t) - 1
```

External flows at start of day; contributions positive, withdrawals negative; purchases/redemptions/switches internal.

### 4.2 Modified Dietz

```
R = (V_end - V_start - sum(CF_i)) / (V_start + sum(w_i × CF_i))
w_i = (T - t_i) / T
```

`T` is the inclusive calendar-day count; flows at start of day. The fixture gives `3.7895%` versus TWR `3.3421%` on the same cash flows.

### 4.3 XIRR

```
sum(CF_i / (1 + r)^((d_i - d_0)/365)) = 0
```

Investor perspective: contributions negative, withdrawals and terminal value positive. A scan detects multiple roots; Newton-Raphson with bisection fallback solves a single root; the result carries an explicit status.

### 4.4 K1/K2 fixture

| Figure | K1 (known 31 Jan 09:00) | K2 (known 5 Feb 11:00) | Delta |
|---|---:|---:|---:|
| Units | 200.000 | 240.000 | +40.000 |
| Cash | 90,000.00 | 88,000.00 | -2,000.00 |
| Value | 100,400.00 | 100,480.00 | +80.00 |
| TWR | 0.4000% | 0.4800% | +8.00 bp |
| XIRR | 4.8125% | 5.8001% | +98.76 bp |

## 5. Alternatives considered and why they were rejected

| Alternative | Why rejected |
|---|---|
| Store only current transaction rows | Loses prior values; cannot reproduce a K1 report; the core business problem is record reconstruction. |
| Store only a PDF report | Not value-for-value comparable; cannot attribute a delta to a transaction revision. |
| Treat a switch as withdrawal + contribution | Creates a false external flow and distorts TWR/XIRR. |
| Treat every cash movement as an external flow | Makes a purchase look like new client money; TWR neutralises the wrong thing. |
| Use binary floating point | Breaks reconciliation and replay at the cent level; Decimal/NUMERIC is required. |
| Round units half-up everywhere | Can over-debit an amount-instructed purchase or create negative switch residual cash. |
| Return the first XIRR root | Arbitrary when multiple roots exist; the result would be indefensible. |
| Reuse FundLens internals directly | Couples to an undocumented local database; a stable read-only contract is safer. |
| Reimplement AMFI scheme mapping | Risks mapping the same scheme differently in two projects; reuse FundLens. |
| Claim GIPS/SEBI compliance | The prototype does not implement the full operational and legal requirements; the claim would be false. |

## 6. Three likely interview questions and defensible answers

### Q1. Why do you need both valid time and knowledge time? Isn't an `updated_at` column enough?

**Answer:** `updated_at` tells you when a row was last changed, but it overwrites the prior value. If a purchase amount is corrected from 10,000 to 12,000, an `updated_at` column leaves only 12,000. A report generated before the correction said 10,000, and that report must remain reproducible. Valid time tells you when the purchase economically applies; knowledge time tells you which version the system knew. The K1/K2 fixture shows the K1 report keeping 200 units and 0.4000% TWR while the K2 restatement shows 240 units and 0.4800%. Both are true at their respective knowledge times.

### Q2. Why are TWR and XIRR different, and when would you show each?

**Answer:** TWR removes the effect of external cash-flow timing, so it measures the portfolio's investment performance. XIRR is money-weighted: it solves for the annualised rate on the investor's dated cash flows, so it reflects when the investor put money in and took it out. In the fixture, two 1,000 contributions and a 2,200 terminal value give TWR 15.2381% but XIRR 6.5248%, because the second contribution had only one year to grow. A performance analyst uses TWR to judge the manager or strategy; an investor uses XIRR to understand their own experience. The dashboard must label them separately and must not compare them without stating the period and annualisation basis.

### Q3. Why does a switch need a special model instead of two ordinary transactions?

**Answer:** A switch is an internal movement: the investor does not add or remove money. If it is modelled as a withdrawal plus a contribution, TWR and XIRR treat it as an external flow and distort the return. The switch must be one atomic group: redeem source units, compute proceeds, buy target units, and credit any rounding residual. Both legs succeed or fail together. In the fixture, 100 source units at 20.0000 produce 2,000.00; the target NAV is 30.0000; ROUND_DOWN buys 66.666 units for 1,999.98 and leaves 0.02 cash. The investor's total value is conserved, and no external flow is recorded.

## 7. Limitations and assumptions

- The FundLens live database query was intentionally not executed under Option A. The contract is verified at schema/source-file level; this is an explicit M0 limitation, not a pending authorisation.
- The 86-files-on-disk vs 85-registered difference has been reconciled in `docs/FUNDLENS_FILE_RECONCILIATION.md`; the duplicate 2006 range is consistent with the extra file and affects only out-of-scope IDCW values.
- The synthetic generator is designed, not implemented. Its parameters are proposed and may change before M2.
- The sensitivity config is a draft. It must be frozen before the study runs.
- The methodology fixtures use illustrative round NAVs, not real market values. The real NAV paths are used later for the sensitivity study and synthetic account valuations.
- No test has been run against the production code because no production code exists yet. The fixtures are the expected answers, not evidence that the implementation passes.
- No Jira project exists; by Vicky's direction, none will be created or claimed.
- The project is an educational prototype, not a production system or a regulatory-compliance claim.
