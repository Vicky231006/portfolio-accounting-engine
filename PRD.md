## 1. Executive summary

Build a portfolio-accounting and performance-reporting system for a simulated wealth-management operation. It maintains account-level cash and mutual-fund positions, values them with real AMFI NAV observations, calculates performance, accepts backdated corrections, and reproduces both the original and corrected versions of historical reports.

The business outcome is the product: **a performance analyst can explain what a portfolio was worth, what the system knew when a report was issued, what changed later, and why reported performance moved.** Bitemporal modelling is the auditability mechanism, not a database demo.

Inputs: real public AMFI NAVs (via FundLens); seeded, explicitly synthetic investors, accounts and transactions. Stack: PostgreSQL (ledger, history, marts), Python (adapters, calculations, generator, orchestration), Power BI (dashboard), GitHub Actions (CI).

This is an educational prototype. It is not a production portfolio-management system, a client system of record, investment advice, or a claim of regulatory compliance (including GIPS).

## 2. Problem statement

A portfolio operations or performance team must answer two different questions about the same historical date: (1) what was economically effective then, and (2) what had the system been told by the time a report was produced? An overwrite-in-place table cannot answer both after a backdated correction.

### 2.1 Users

| User | Main question | System support |
| --- | --- | --- |
| Portfolio operations analyst | What transactions and positions are currently recognised for an account? | Ledger, positions, correction history |
| Performance analyst | What was the account's return for a period, using what was known at time K? | TWR, Modified Dietz, XIRR, report replay |
| Operations / team lead | Which reports changed after corrections, and why? | Restatement register, impact attribution, dashboard |

### 2.2 Worked scenario (illustrative numbers)

- **10 Jan (effective date):** purchase of INR 10,000 in scheme S, recorded at simulated time 10 Jan 18:00 UTC. Allotment NAV 50.0000, so 200.000 units.
- **31 Jan:** report R1 generated at K1 = 31 Jan 09:00 UTC and archived.
- **5 Feb:** an authorised correction recorded at K2 = 5 Feb 11:00 UTC establishes the amount was INR 12,000. Units become 240.000 and the cash leg is corrected in the same correction group.
- Query with `known_as_of = K1` must reproduce R1 exactly. Query with `known_as_of = K2` must use 240 units and the restatement register must show the delta, the changed transaction version and the reason code.

## 3. Goals and success criteria

1. Maintain synthetic account transactions without destructive overwrites of business history.
2. Value fund holdings and cash as of a chosen effective date and knowledge timestamp.
3. Calculate and clearly distinguish TWR, Modified Dietz and XIRR.
4. Accept backdated corrections with reason, source, actor and lineage, rejecting any that would create an invalid state.
5. Reproduce archived reports exactly and produce restatement reports with attribution.
6. Quantify how reporting errors move returns, using real NAV paths (sensitivity study, FR-B13).
7. Prove correctness with hand-computed fixtures, independent references, invariants and reproducible evaluation.

**Definition of success.** `make reproduce` rebuilds the seeded dataset, calculations, evaluation and `RESULTS.md` from an empty database; replay acceptance tests pass; every headline metric carries its baseline or reference, sample size and data provenance. A positive result is not required; correctness, explainability, replayability and transparent limitations are.

**Honesty rules.** (a) No claim of real clients, accounts, AUM, users or real-world prevalence. (b) Synthetic data is labelled in the README, dashboard footer, data card, results and resume wording. (c) Thresholds and scenarios are fixed before results are inspected. (d) Replay success is reported as a count, not as an improvement percentage.

## 5. Data and provenance

### 5.1 Market data (real)

Use the AMFI NAV observations already sourced by FundLens. No artificial NAVs. Consume a documented, versioned NAV export or a thin adapter on the same data contract; do not fork scheme-mapping logic. Record per observation: scheme identifier and name as received, plan and option, NAV date and value, source file/URL, retrieval timestamp, source checksum or snapshot ID, import timestamp, row-level validation outcome. If FundLens has no stable export, build the smallest repeatable contract and document its schema and checksum.

### 5.2 Synthetic accounts and transactions

Generated from a deterministic seed and labelled synthetic everywhere. Configurable: seed; investor and account counts; opening dates; transaction counts and date range; transaction-type mix; SIP schedules; correction frequency and backdating delay; amount distributions.

**Simulated clock.** The generator owns knowledge time. Every transaction and correction carries a simulated `recorded_at` (UTC) produced by the generator, and report snapshots use simulated generation timestamps. Without this, K1 and K2 collapse to wall-clock "now" and replay is meaningless. Wall-clock time is used only for audit metadata about the pipeline run itself.

### 5.3 Allotment and valuation NAV rules

- Purchases and SIP instalments are instructed by **amount**; units are derived: `units = quantize(amount / NAV(allotment_date))`.
- Redemptions are instructed by **units**; proceeds = `quantize(units x NAV(allotment_date))`.
- `allotment_date` = effective date if a NAV exists for the scheme that day; otherwise the next date with a NAV, within a configurable limit (default 5 calendar days), else the generator does not create the transaction and a corrected transaction is rejected. Cut-off times are out of scope.
- Rounding policy (default: units 3 dp, amounts 2 dp, NAV as published) is configurable and documented in `docs/METHODOLOGY.md`.
- Valuation uses the NAV on the valuation date. If missing, apply the documented policy: carry the last NAV forward up to a configurable limit (default 5 calendar days), flag the value as stale and report it separately; beyond the limit, valuation fails explicitly. No silent forward-fill.

### 5.4 Data card

`docs/DATA_CARD.md`: AMFI source URL, retrieval date, terms-of-use review, fields used, coverage, known gaps, scheme-mapping behaviour; generator specification and the synthetic disclosure.

## 6. Domain definitions

**Valid (effective) date:** the business date a transaction economically applies. **Knowledge (recorded) time:** the simulated UTC timestamp at which the system accepted that version. **As-of state:** positions and cash effective through a valid date, using only versions known at a requested timestamp.

### 6.1 External versus internal flows

- Contributions and withdrawals are external flows for TWR. Purchases and redemptions move value between cash and units and are internal.
- A `SIP_INSTALMENT` has a contribution leg (external, counted once) and a purchase leg (internal). A `SWITCH` is a linked redemption and purchase and is never an external flow.

### 6.2 Transaction semantics

| Type | Instruction field | Portfolio effect | Performance treatment |
| --- | --- | --- | --- |
| `CONTRIBUTION` | amount | Adds cash | External flow in |
| `WITHDRAWAL` | amount | Removes cash | External flow out |
| `PURCHASE` | amount | Cash down, units up | Internal |
| `REDEMPTION` | units | Units down, cash up | Internal |
| `SIP_INSTALMENT` | amount | Linked contribution and purchase | Contribution external once; purchase internal |
| `SWITCH` | units out | Linked redemption and purchase | Internal |

### 6.3 Correction semantics

A correction is a lifecycle action on a prior revision, not a new economic type. It may change only **instruction fields** (effective date, amount or units, scheme via reverse-and-replace). Derived fields (NAV used, units or proceeds, cash legs) are recomputed in the same atomic correction group so linked legs always balance. Units are never edited directly. Each correction carries: business transaction ID, prior and new revision IDs, correction type (replace, void, reverse-and-replace), reason code, explanatory note, synthetic source reference, synthetic operator ID, effective date and `recorded_at`.

**Validity rule.** A correction is rejected (and logged) if the resulting corrected history would create negative units, negative cash beyond configured rules, or break a linked-leg balance for any later transaction. Rejections are part of the audit output.

## 8. Financial methodology (document in `docs/METHODOLOGY.md` before calculations are complete)

**Valuation.** `position_value = units x NAV`; `portfolio_value = sum(position_value) + cash`.

**TWR** (external flows at start of day; state the sign convention for `CF_t`): `r_t = (V_t - V_(t-1) - CF_t) / (V_(t-1) + CF_t)`; `TWR = product(1 + r_t) - 1`. Internal purchases, redemptions and switches are not flows.

**Modified Dietz:** `R = (V_end - V_start - sum(CF_i)) / (V_start + sum(w_i x CF_i))`, `w_i = (T - t_i) / T`. State the day-count and flow-timing convention; test zero-flow and same-day-flow cases.

**XIRR:** solve `sum(CF_i / (1 + r)^((d_i - d_0) / 365)) = 0` using investor-perspective flows (contributions negative; withdrawals and terminal value positive). Newton-Raphson with a bounded bisection fallback and explicit no-root and non-convergence results (status, iterations, reason). Test multiple-sign-change and no-root cases.

**Wording.** Use "GIPS-style TWR conventions" only when the documented method follows them; never "GIPS-compliant".

## 9. Bitemporal model and audit

Two independent axes: business-effective date and system knowledge interval. Preferred design: an immutable append-only revision table plus a rebuildable version projection. If a physical `tstzrange` system period is used, enforce per-business-transaction non-overlap with a PostgreSQL GiST exclusion constraint (`btree_gist`); if another representation is chosen, document why and provide equivalent no-overlap and as-of tests. Any mutable projection must be rebuildable from the revision history; never claim every table is immutable if a projection is updated.

**Suggested tables (not binding):** `investor`, `account`, `scheme_ref`, `nav_observation`, `txn_business`, `txn_revision` (with `correction_group_id`, `prev_revision_id`, `system_period`, reason, source, actor), `txn_version_current` (projection), `cash_ledger`, `unit_ledger`, `report_snapshot`, `restatement_item`, `invariant_run`, `sim_clock_log`, `pipeline_run`.

## 10. Report replay and restatement workflow

1. Generate a report for account A, period P at knowledge time K1; persist the snapshot with calculation and data-version metadata.
2. Record a backdated correction at K2 > K1.
3. Re-run with K1: canonical payload and hash must match the archive.
4. Run with K2: output reflects the correction.
5. Generate the restatement comparison: changed holdings, valuation, TWR, Modified Dietz and XIRR, changed transaction versions, reasons.

Use deterministic formatting and the documented rounding policy.

### 12.2 Sensitivity study design (FR-B13)

Commit `config/sensitivity.yaml` **before** running and do not change it after seeing results.

- **Paths:** a fixed rule for selecting real Growth-plan scheme NAV series (for example all schemes with at least a stated history length in stated categories, with a seeded sample cap). Log n.
- **Windows:** a fixed grid of start dates and a fixed window length (for example 12 months).
- **Investor behaviour:** a deterministic monthly SIP of a fixed amount. This is a rule, not random synthetic behaviour.
- **Scenarios:** (a) one instalment backdated by d business days for d in a fixed set; (b) one instalment mis-sized by x% for x in a fixed set; (c) a missed correction, meaning the report keeps the wrong flow.
- **Outputs:** for each scenario, the change in reported TWR, Modified Dietz and XIRR in basis points versus the correct history: median, p95, and the share exceeding configured bp thresholds, all with n. For E9, the distribution of XIRR minus TWR by window start and its relation to the window's drawdown.
- **Interpretation limits:** the correction magnitudes are controlled parameters, not observed error rates. State this in the README. The study measures how sensitive reported returns are to errors; it does not measure user benefit.

## 14. Testing requirements

- Unit tests per calculation against hand-computed examples (contribution, withdrawal, purchase, switch, SIP, same-day flow, zero flow).
- Property tests: scaling all flows and values by a constant leaves returns unchanged; no external flows means TWR equals portfolio return; no-flow XIRR matches the period return; as-of results are deterministic.
- Temporal tests: a correction recorded after K1 cannot alter a `known_as_of = K1` query; it alters K2 views where effective; overlapping system periods are rejected.
- Replay tests: archived reports reproduce from stored metadata.
- Integration tests: migrations, seeded data, NAV import, valuation, correction, restatement, dashboard marts.
- Negative tests: duplicate versions, invalid scheme mapping, missing NAV, invalid signs, negative positions, malformed correction references, corrections that would create negative downstream positions.
- Independent reference tests for XIRR and TWR.
